# Filter Data & XAI Provenance — Findings

> Plain-language summary of the read-only audit in this directory. Every claim below traces
> to `FILTER_DATA_PROVENANCE.csv`, `FILTER_XAI_CLAIM_MATRIX.md`,
> `ARTIFACT_TAXONOMY_ALIGNMENT.md`, or `EXTERNAL_FILTER_XAI_RISK_REGISTER.md` in this same
> directory. Nothing here modifies `pipeline.py`, any checkpoint, any split file, or any
> existing template/schema.

## How many data families actually feed the filter classifier's training data?

**Six, by family ID, across two genuinely different provenance types**:

- **Self-built, paired (A1, A2, A3, F)** — all generated by this project's own
  `filters/*.py` code applied to AIGuard/real, LFW, or AIGuard/fake base images. All four are
  variations on the same generation method, not independent data sources in a statistical
  sense.
- **External RetouchingFFHQ (B, C, D)** — a public academic dataset (arXiv:2307.10642) built
  from real commercial beautification-app outputs (Megvii and Alibaba confirmed; the
  unbranded "four_process" block's company is not recoverable from local files).
- **Absent (E)** — Tencent, the third company RetouchingFFHQ's paper describes, was never
  obtained (pending, unapproved application, per `docs/Dataset 清單.md`). No other
  retouch/filter data source of any kind was found anywhere in this repo.

Of these, **A1, A2, A3, B, C feed actual v8.11 production TRAINING** (confirmed by grepping
the current production filter split, `splits/v86_train_filter.txt`, in this round — it
contains `filter_data/` (self-built), `FFHQ_megvii_four_process/`, and `FFHQ_four_process/`
paths). **D (Alibaba) is deliberately eval-only**, held out since v8.6 specifically to serve
as a cross-company OOD benchmark. **F is used for hard-negative training**, separately from
the main filter-class split.

## Which families are self-built paired data?

A1, A2, A3, and F — all four have genuine before/after pairing, filter parameters, and
constructible pixel-level/LAB-diff/landmark-displacement ground truth, because this project's
own code both applies the filter and controls both sides of the pair. This is the ONLY
provenance type in this project with that property.

## Which are RetouchingFFHQ/app-like data?

B (`FFHQ_four_process`, unbranded), C (`FFHQ_megvii_four_process`, confirmed Megvii), and D
(`FFHQ_ali_process`, confirmed Alibaba). All three are confirmed, via an exhaustive
already-existing audit (`results/retouchingffhq_pair_audit_20260812.json`), to have **zero**
locally-available original (pre-retouching) FFHQ images — the raw NVIDIA FFHQ 70K dataset was
never downloaded, only the processed outputs exist. B and C additionally apply all 4
beautification operations simultaneously to every image (confirmed via `four_process.txt`'s
per-image parameter records), so even if pairing existed, there would be no single "type"
label to validate against for those two blocks. D is structurally different — it has
genuine single-operation folders (`EyeEnlarging_NN`, `FaceLifting_NN`, `Smoothing_NN`,
`Whitening_NN`) — but its own type ground truth has never been used to evaluate
`artifact_classifier_v3`, confirmed by reading `AIGuard/eval_ali_ood_v811.py` (it only checks
the coarse filter/not-filter decision, never calls the 4-way type classifier).

## Which filter XAI claims are valid ONLY for self-built data?

Per `FILTER_XAI_CLAIM_MATRIX.md`: **eyes-region-level text, paired-GT-backed localization,
and pixel-level/LAB-diff validation are ALLOWED only for families A1/A2/A3** (and
ALLOWED_WITH_CAVEAT for F, with a documented type-accuracy caveat for whitening/eye_enlarging
on fake-image composites). For every external family (B/C/D), these three claim types are
**NOT_SUPPORTED** — the only thing a Grad-CAM++ heatmap can honestly be described as for an
external-source image is a model-attention visualization, not a validated localization.

## What's the safest output when an external FFHQ/Alibaba/Megvii filter image goes through the pipeline?

Based on this audit: **`final_class=filter` (or `real`/`fake`) is the only claim tier with
direct evidence at the confidence level production currently implies** — and only for
Alibaba (family D), which is the one external family with an actual held-out accuracy number
(98.1% filter-detection recall, matching the current v8.11d/v811 production checkpoint pair).
For Megvii/unbranded (B/C), even the coarse filter-class training exposure exists, but no
held-out per-family accuracy number for THEM specifically was located (they're folded into the
overall Layer2 training data, not separately evaluated). **Exact artifact_type, any
region-naming text (eyes or otherwise-specific), and any Grad-CAM++ caption implying
GT-validated localization should NOT be produced for any of B/C/D** under the current
evidence — the honest fallback is class-only output with, at most, a generic
"beautification-style processing detected" description and a heatmap labeled as a
visualization, not a validated location.

## Is the pipeline currently at risk of wrongly applying one of the 4 self-built artifact templates to an external filter image?

**Yes — this is the audit's top finding, per `EXTERNAL_FILTER_XAI_RISK_REGISTER.md` risks
#1-#3.** `pipeline.py`'s `classify_artifact()` runs the same 4-way `artifact_classifier_v3`
regardless of where the input image came from — there is no source-family detection step, and
none of the model's own training/eval history includes evidence that its type predictions are
reliable outside the self-built family it was trained on (confirmed: `artifact_classifier_v3`
is trained EXCLUSIVELY on `filter_data/clean_output/clean_paths.txt`, i.e. family A1 only,
per direct reading of `AIGuard/train_artifact_classifier_v3.py`). For a RetouchingFFHQ-style
external image reaching the pipeline today: the system WILL output one of the 4 exact types
with a confidence-gated `unknown_filter` fallback that was calibrated for self-built data, and
the resulting template sentence WILL name a specific artifact type and (depending on that
type) a specific facial region — with no validated basis for that specificity on this input's
actual source distribution. This is a real, currently-live overclaim risk, not a hypothetical
one.

## Recommended next stage

Ranked by cost/evidence-value, based on what this audit found rather than a generic wishlist:

1. **Score `artifact_classifier_v3` against `FFHQ_ali_process`'s own folder-name ground
   truth** — this is the cheapest possible next experiment (the ground truth already exists,
   no new data collection needed, just a new eval script analogous to
   `AIGuard/eval_ali_ood_v811.py` but calling `classify_artifact()` instead of stopping at
   `hierarchical_predict()`). This single measurement would resolve the single largest
   evidence gap this audit found (risk #1) and directly informs whether family D's
   "structurally aligned" taxonomy (see `ARTIFACT_TAXONOMY_ALIGNMENT.md`) is ALSO
   *functionally* aligned.
2. **Design and pilot an `unknown_retouch`/`mixed_retouch` output path** for families B/C,
   informed by #1's result — per `ARTIFACT_TAXONOMY_ALIGNMENT.md`, this is a data-format
   mismatch (single-label classifier vs. inherently multi-operation images), not something
   more training data on the current format would fix.
3. **External filter taxonomy / app-specific evaluation** as a broader follow-on once #1 and
   #2 have results — worth doing, but #1 is strictly cheaper and answers the most urgent
   open question first.
4. Scale-normalized generator v2 and multi-label retouch modeling are both reasonable
   longer-term directions but are architecture/data-generation changes, out of scope for
   evidence gathered in this read-only round to recommend committing to yet.

---

## Final report

1. **Number and names of filter data families**: 6 families (A: self-built, split into
   3 sub-sources A1/A2/A3 by base-image origin; B: RetouchingFFHQ unbranded four_process;
   C: RetouchingFFHQ Megvii four_process; D: RetouchingFFHQ Alibaba single-operation; E:
   Tencent/other, confirmed absent; F: fake+filter composite, self-built on AIGuard/fake).
2. **Families with full paired GT**: A1, A2, A3, F (all self-built). B, C, D have zero —
   confirmed by an already-existing exhaustive audit, not re-derived this round.
3. **Families that can only support filter detection, not type/region explanation**: B, C, D
   (all three RetouchingFFHQ blocks) — B/C additionally cannot even honestly support a
   single-type label because their images have all 4 operations applied simultaneously; D
   could structurally support type-level claims but has never been evaluated for it.
4. **Pipeline's biggest current overclaim risk for an external filter case**: the 4-way
   `artifact_classifier_v3` (trained exclusively on self-built data) runs unconditionally on
   any image the main classifier calls "filter," producing a specific type + region-naming
   template sentence with no source-awareness and no validated basis for that specificity on
   RetouchingFFHQ-style inputs.
5. **Most research-valuable next technical question**: does `artifact_classifier_v3`'s type
   prediction actually agree with `FFHQ_ali_process`'s own ground-truth folder labels? This is
   answerable today, cheaply, with existing data, and directly resolves the audit's largest
   evidence gap.
6. **Confirmed**: `pipeline.py`, all checkpoints, all split files, all existing results, and
   the existing template text / `ARTIFACT_REGION_MAP` / JSON schema were read but not
   modified. No training or evaluation was rerun. No git commit was made. All new files are
   under `results/phase2/filter_data_xai_provenance_audit_20260814/` plus one new
   root-level script (`p2_gen_lineage_figure.py`) used only to render the lineage figure.
