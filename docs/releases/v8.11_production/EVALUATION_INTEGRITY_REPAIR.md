# Evaluation Integrity Repair — v8.11 Production (P0)

> Companion to `results/releases/v8.11_production_20260813/`. This document is the narrative
> record of the bug found, the fix applied, and the before/after numbers. It supersedes
> nothing in `docs/releases/v8.11_production/RELEASE_RESULTS.md` — it's the evidence that
> upgrades several of that document's UNVERIFIABLE items to VERIFIED. No existing file was
> overwritten, moved, or deleted to produce this repair.

## The bug, found in each of the 4 scripts

All four scripts resolved `L1_WEIGHTS` the same way:

```python
L1_WEIGHTS = sys.argv[1] if len(sys.argv) > 1 else str(BASE / "shufflenet_v2_layer1_v811c.pth")
```

Running any of them with **no arguments** — the natural thing to do when you just want "the
v8.11 numbers" and don't know the exact filename convention — silently loaded
`shufflenet_v2_layer1_v811c.pth`, a **superseded** checkpoint (Layer1c was replaced by
Layer1d on 2026-08-10 per TODO.md's own round-4 hard-negative fine-tune entry). `L2_WEIGHTS`
happened to already default correctly to `shufflenet_v2_layer2_v811.pth` in all four scripts,
so only Layer1 was ever silently wrong — but that's enough to shift every gate number.

| Script | Old default L1 | Old default L2 | Output before fix |
|---|---|---|---|
| `eval_v811_gates.py` | v811c (wrong) | v811 (correct) | stdout only, no file |
| `AIGuard/stress_test_v811_pipeline.py` | v811c (wrong) | v811 (correct) | auto-named by weight tag, written to `results/` root |
| `AIGuard/eval_ali_ood_v811.py` | v811c (wrong) | v811 (correct) | stdout only, no file |
| `AIGuard/eval_robustness.py` | v811c (wrong) | v811 (correct) | auto-named by weight tag, written to `results/` root |

## How each script was fixed (diff-level summary)

For all 4 scripts, the same pattern of change was applied:

1. **Replaced** the `sys.argv[1]/sys.argv[2]` positional-with-default resolution with
   `argparse`, requiring `--layer1-weights` and `--layer2-weights` explicitly. No default
   value of any kind — omitting either flag prints `"ERROR: --layer1-weights and
   --layer2-weights are required. Refusing to fall back to a default checkpoint."` and exits
   with code 1 (verified: all 4 scripts tested with no arguments before running any real
   evaluation, all 4 confirmed to exit 1 with this exact message).
2. **Added** a fail-closed existence check: if the given path doesn't point to a real file,
   print `"ERROR: Layer{1,2} weights not found: <path>"` and exit 1.
3. **Added** a provenance block computed once at script start: SHA256 of both checkpoint
   files, SHA256 of the script file itself (`Path(__file__).resolve()`), the git commit hash
   (`git rev-parse HEAD`, read-only), the exact command line (`" ".join(sys.argv)`), and a UTC
   timestamp. This block is printed to console on every run and embedded in every JSON output.
4. **Redirected** all output writing to `results/releases/v8.11_production_20260813/` (newly
   created, never previously existed), with filenames encoding the weight tags, the eval name,
   and the run date (e.g. `core_gates_v811d_layer2v811_20260813.json`). Each script now
   refuses to overwrite an existing file at its computed output path (checks `.exists()` and
   exits 1 if the target is already there) — for `eval_v811_gates.py` and
   `AIGuard/eval_ali_ood_v811.py`, this is entirely new output-writing capability (they
   previously wrote no file at all); for the other two, it's a redirect of the pre-existing
   auto-naming logic into the isolated release directory.
5. **No other logic was changed.** Model architecture, inference forward pass, metric
   formulas (recall/AUROC/confusion-matrix computation), and split-file reading logic are
   byte-identical to before the fix — confirmed by diff review during editing (only the
   argument-resolution block, provenance printout, and output-path/write block were touched).

All 4 scripts were syntax-checked (`python -m py_compile`) and their fail-closed behavior was
explicitly tested (invoked with zero arguments, confirmed exit code 1 with the required error
message) **before** any real evaluation was run against them.

## Can the release `provenance_status` be upgraded from PARTIALLY_VERIFIED?

**Yes, upgraded to VERIFIED for the static/desktop evaluation scope — with the iPhone
benchmark gap explicitly carved out and still Pending.**

The original `PARTIALLY_VERIFIED` status (see
`docs/releases/v8.11_production/RELEASE_MANIFEST.json`) was justified by three concrete gaps:

1. Alibaba OOD 98.1% had no backing file — **RESOLVED**, now backed by
   `alibaba_filter_ood_v811d_layer2v811_20260813.json`.
2. True Test paired balanced accuracy 81.1% had no backing file — **RESOLVED**, now backed by
   `truetest_paired_v811d_layer2v811_20260813_provenance.json` + console log.
3. Four scripts silently defaulted to a superseded checkpoint, an active footgun risk for
   future re-runs — **RESOLVED**, all four are now fail-closed and were verified to reject
   no-argument invocations before any real evaluation was trusted.

All three gaps that justified PARTIALLY_VERIFIED are now closed. **However**, the iPhone
on-device benchmark remains genuinely not done — this was never one of the three gaps that
caused the PARTIALLY_VERIFIED rating (it was already tracked separately as the one open
Freeze Gate item), so it does not block an upgrade to VERIFIED for the *evaluation-integrity*
scope this repair addresses, but the release as a whole should still carry an explicit
`"iPhone benchmark: Pending"` caveat wherever `provenance_status` is quoted, so nobody reads
"VERIFIED" as "fully deployment-verified." **This document does not itself edit
`RELEASE_MANIFEST.json`** — the person/process using this record should update that file's
`provenance_status` field deliberately, with the caveat above, rather than this document
silently asserting the change.
